# R22 · Discuss a change

## Goal

A chat with the assistant about a change, grounded in Keel's documents, that ends in a checked proposal; the user's Agree writes the change request package and keeps the discussion with it.

## Scenarios that prove it

- `features/discuss-a-change.feature` (all scenarios).
- Unit tests: `proposal.test.ts` (schema, extraction of the fenced block, checks), `context.test.ts` (sources, names-only code map, sections pulled by ID, budget and summary), `discussion-file.test.ts` (write, read, move on Agree, park), `keys.test.ts` (key patterns held, never written).

## Data

- Discussion file `.keel/discussions/DSC-NNNN.md` from `discussion@1`. Front matter: `id`, `title`, `status: open | parked | cr`, `cr`, `model`, `style`, `started`, `sources` (the ticked ones), `attachments` (names only). Body: one `### <author> · <date time>` heading per message; summaries under `### Summary of messages 1–N`; proposals as ` ```keel-proposal ` blocks; edits as `### <user> edited the proposal` with the fields changed.
- Proposal (zod, from the last ` ```keel-proposal ` block of a reply):
  ```json
  {
    "title": "string",
    "why": "string",
    "what": ["string"],
    "requirements": [{ "id": "REQ-005 | new", "change": "new | changed | removed", "text": "string" }],
    "impact": [{ "area": "string", "requirements": ["REQ-005 | new"], "what": "string" }],
    "scenarios": [{ "title": "string", "requirement": "REQ-005 | new" }],
    "tasks": [{ "title": "string", "files": ["path (new)"] }],
    "decision": { "title": "string", "alternatives": ["string"] },
    "dependsOn": ["CR-0009"],
    "screens": ["string"]
  }
  ```
- Checks: `{ kind: 'ok' | 'warn' | 'error', text }[]`; an `error` (unknown requirement ID, duplicate of an open change request) disables Agree until edited.
- Change request header: new optional field `discussion: DSC-NNNN`.
- Settings: `ModelTask` gains `'discussion'` (label "Discussion"); `modelChoice` falls back to `documents` when unset.
- Styles: front matter gains `kind: brainstorm | discussion` (missing means brainstorm); config gains `discussion_style` (default `requirements-partner@1`).

## Steps

1. Discussion files and the template; Discussion model task; style `kind`. Commit.
2. Context builder with budget and summaries; key check. Commit.
3. Streaming chat screen and route, with Stop, starters and the side panel. Commit.
4. Proposal: format in the prompt, extraction, validation, retry once, checks, card with Edit and Keep talking. Commit.
5. Agree: IDs, R19 writer, move the discussion, one commit; Park; Earlier discussions; link from the change request. Commit.
6. Scenarios green, docs. Commit.

## Notes

- The model never writes files and never chooses IDs.
- Only the Agree button creates a change request; chat text never does.
- Discussion files are committed; they must never contain attachment contents or anything that matched a key pattern.

## As built

- **Model and style.** `ModelTask` gains `discussion` ("Discussion" in Settings › Model per task, checked by the Startup check like the others); `savedModelChoice` falls back to the Spec and plan model, and Ollama's default is the largest model. Styles have `kind: brainstorm | discussion` (missing means brainstorm); `listStyles(root, kind)` keeps Explore to brainstorm styles; the Library shows a "Discussion styles" group. `.keel/config.yml` gains `discussion_style` (default `requirements-partner@1`), chosen in Project setup › Discussion style.
- **Discussion files** (`src/lib/discussion/file.ts`): `.keel/discussions/DSC-NNNN.md` from `discussion@1` (its guidance comments dropped). Front matter: id, title, status, cr, model, style, started, sources, attachments (names). Body: `### <author> · <YYYY-MM-DD HH:MM>` per message, `### Summary of messages 1–N`, `### <user> edited the proposal · <time>` (the fields changed and the full edited block). A line starting `### ` inside a message is written as `\### `. Writing refuses any entry that looks like a key. Each finished turn is committed with `commitSquashing`, so a run of messages is one Keel commit and leaving the screen loses nothing (instead of a commit on leaving, which raced with Agree in the browser). Park is its own commit.
- **Keys** (`keys.ts`): `sk-…`, `gh?_…`, `github_pat_…`, `AKIA…`, `xox?-…`, private key headers, and a long hex or base64 token after key, token, secret or password. Held in the browser and again by the server, before anything is written or sent.
- **Context** (`context.ts`, `prompt.ts`, `turn.ts`): sources intent, requirements, decisions (ADR titles and design choices), plan (task titles and status), open change requests, code map (names, absent when the code map setting is Off) and standards (names, off). IDs named in the conversation (REQ, ADR, CR, T/R tasks) add the full section, from ticked sources only. Attachments: up to 100 KB of text, refused when the name may hold keys (CR-0015 patterns) or the text looks like a key; sent with that message only, kept by name. Tokens are characters / 4 against the Ollama model's context length (32k when unknown); above 60% the oldest messages (all but the last four) are summarised with one Discussion call and the summary replaces them in what is sent.
- **Proposal** (`proposal.ts`): the last ```` ```keel-proposal ```` block, validated with zod (IDs are `REQ-NNN` or `new`). The route asks once more with the zod error when the block is unreadable; if still unreadable the reply is shown as text with "The proposal could not be read; ask the assistant to propose again". Checks without a model: unknown requirement IDs and a changed/removed requirement without an ID are errors (Agree disabled); files outside the code map and not marked `(new)`, unknown `dependsOn`, and intent constraints the proposal touches are warnings; an open change request with overlapping requirements and a similar title is an error.
- **Agree** (`agree.ts`): new REQ IDs from `next_req` and the highest in the documents (config saved in the same commit), the CR via `createChange` (new `commit: false` option; header `discussion: DSC-NNNN`; Requirement changes and Impact rows filled from the proposal), tasks R-numbers from `nextTaskNumber` in a plan, scenarios accepted into the plan so `packageFiles` writes the feature, a draft decision record in `changes/CR-NNNN/decisions/NNNN-<slug>.md` (next number across `docs/decisions` and change folders), `changes/README.md`, and the discussion moved to `changes/CR-NNNN/discussion.md`. One commit: "Keel: CR-NNNN from discussion DSC-NNNN". The change request is a Draft (significant when it adds or changes a requirement).
- **Screen** (`src/app/(project)/discuss/`, `src/app/api/discuss/route.ts`): streamed JSON lines (started with tokens and pulled IDs, chunks, done), aborted by Stop (the partial reply is saved with "(Stopped)"). The card shows "new" for new requirements, tasks and decisions, the checks, and Agree, Edit (a form for every field) and Keep talking. "Typing “yes” creates nothing: use Agree on the proposal" shows under the message box while a proposal waits. After Agree, the card lists the files written and offers Open CR-NNNN. Starters: `/discuss?start=…` from roadmap Next and Later items, readiness advice (Keel folders), the approved-document note, and on the empty screen. Screens named by the proposal are listed; the clickable-mock prompt stays on the Spec page (not generated here).
- **Fake provider**: discussion replies (a proposal on the first reply, plain text for "yes"), records each request in `KEEL_FAKE_LOG.discuss`, and reads `discussion: no-proposal | invalid | unknown-req` from the control file.
