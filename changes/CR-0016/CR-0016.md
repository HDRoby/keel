# CR-0016: Discuss a change, a chat that ends in a change request

## Why

The owner discusses new requirements with an assistant in a chat: the assistant checks the idea against what exists, asks what it needs, offers options with one recommended, and proposes a change request; once the owner agrees, the package is written. Keel should offer the same process, so a change starts as a conversation instead of a blank form, and the conversation is kept for traceability: anyone can see later why a requirement exists.

## What changes

1. **Screen "Discuss a change"** (route `/discuss`, `/discuss/<DSC id>`):
   - main button on the Changes page, next to "New change request" (which stays);
   - item "Discuss a change" in the project menu, after Changes;
   - starters: a roadmap item (Next or Later), an accepted readiness advice item (CR-0015), an edit to an approved document (instead of the plain "raise a change request" note of CR-0003).
   Not available in setup mode.
2. **Chat.** Streamed replies through the existing provider layer (`stream`), with Stop. Markdown in replies (paragraphs, lists, bold, code). One message box with **Attach a file** and **Send**.
3. **Model.** A new model task **Discussion** in Settings › Model per task. When unset it uses the Spec and plan model. The Startup check checks it like the others.
4. **Style.** The assistant follows a discussion style, a versioned skill file like the brainstorm styles: `requirements-partner@1` (in `seed/styles/`, copied into `.keel/styles/`). It says how to discuss: check against existing requirements, decisions and open change requests first; ask before assuming, one or two questions at a time; offer options with one recommended and the trade-offs; name conflicts and duplicates by ID; keep replies short; propose a change request only when the open questions are settled or the user asks. Project setup lets the user pick another discussion style.
5. **What the assistant can see** (side panel, a checkbox per source, per discussion):
   - intent (sections), requirements (full text), design decisions (titles and choices), plan (task titles and status), open change requests (titles and requirements): on by default;
   - code map, names only, following the CR-0013 setting (absent when the setting is Off);
   - standards: names only, off by default;
   - full sections are added when the conversation names them (REQ, ADR, task, CR IDs), and the panel lists which;
   - attached files: only the ones the user attaches, each time. A file matching the CR-0015 secret patterns cannot be attached.
   Nothing else is sent: no other file contents, no keys.
6. **Length.** Keel estimates tokens (characters / 4) against the model's context (from Ollama's model info, or 32k when unknown) and shows "about N of M tokens". Above 60% it summarises the oldest messages with one call; the summary is kept in the discussion file and replaces those messages in what is sent.
7. **Keys typed in the chat.** Before sending, a message that matches a key pattern (`sk-…`, `ghp_…`, `AKIA…`, a long base64 or hex token after `key`, `token`, `secret`, `password`) is held: "This looks like a key. Keel will not send or save it." The user can edit it; it is never written to the discussion file.
8. **Proposal.** When the discussion settles the assistant ends its reply with one fenced block ` ```keel-proposal ` holding JSON in a fixed format (title, why, what changes, requirement changes, impact by requirement, scenarios, tasks with likely files, decision, depends on; see Data in R22). Keel:
   - validates it (zod); an invalid block is asked again once, then shown as plain text with "The proposal could not be read; ask the assistant to propose again";
   - checks it, without the model: changed requirement IDs exist; files are in the code map or marked new; no open change request covers the same requirements with a similar title; constraints in the intent that the proposal mentions are listed as notes;
   - shows it as a **Proposed change request** card, never as text, with **Agree and create the change request**, **Edit**, **Keep talking**.
   The model never chooses IDs: new requirements, tasks and decisions are "new" until the user agrees.
9. **Agreement is a button.** Only **Agree** creates anything. Writing "yes" or "go ahead" in the chat does not; under the message box Keel says so once a proposal is waiting. **Edit** makes every field of the card editable; edits are recorded in the discussion as "Edited by <user>" with the fields changed.
10. **On Agree,** Keel, without a model call:
    - assigns the next free IDs (CR, REQ, task R-number, ADR) with the CR-0013 rules and clash warnings;
    - writes the package with the CR-0013 writer from the templates in Settings: `CR-NNNN.md`, `PROMPT.md`, `tasks/<ID>.md`, `features/<name>.feature` with the scenarios, a draft decision record, `changes/README.md`;
    - moves the discussion to `changes/CR-NNNN/discussion.md` (git mv) and links it from the CR header (`discussion: DSC-NNNN`);
    - commits once: "Keel: CR-NNNN from discussion DSC-NNNN";
    - shows what was written. The change request is a **Draft** and follows CR-0003: a significant change (a requirement added or changed) must be approved before it goes to the agent.
11. **Saved for traceability.** Every discussion is a file from the template `discussion@1`, `.keel/discussions/DSC-NNNN.md`, written after each message and committed (one Keel commit) when the user agrees, parks it, or leaves the screen with new messages. It holds the messages with author and time, summaries, proposals (as their JSON blocks), edits, the context sources used and the model; attachments by name only. A discussion without a change request can be **Parked** and stays in `.keel/discussions/`. "Earlier discussions" lists them with their status (In progress, Parked, CR-NNNN); the change request page links back to its discussion.
12. **Mocks stay outside Keel.** When the proposal touches screens, it lists them; after Agree, Keel offers the CR-0009 clickable-mock prompt for those screens. Keel does not generate mocks.

## Decisions

- New decision record ADR-0019 "A discussion ends in a structured proposal; only the user's Agree creates the change request". Alternatives considered: the model writes the files with tool calls (not reliable across providers, and Ollama models vary); detecting agreement from the user's text (ambiguous).
- Discussions are committed with the project, for traceability (owner decision, 2026-11-22).
