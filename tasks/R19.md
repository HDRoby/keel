# R19 · Change packages as complete as hand-written ones

## Goal

Keel writes change packages with templates and a planning step, so they match the hand-written CR-0003 to CR-0012 in completeness.

## Scenarios that prove it

- `features/change-packages.feature` (all scenarios)

## Data

- `.keel/config.yml` › `templates`: add `change`, `change-prompt`, `task`, `changes-index` (template refs), `codeMap: off | names | files` (default `names`), `changesIndex: auto | off` (default `auto`).
- Change request header: unchanged fields, plus `planned_at` and `package` (list of written files) on Keel requests.
- Task header for change tasks: `change: CR-NNNN` instead of `plan`.

## Files that are likely to change

- `seed/templates/`: add `change-request-v2.md`, `prompt.md`, `task-v2.md`, `changes-index.md` from `changes/CR-0013/seed-templates/`; keep `change-request.md` and `task.md` as v1 for documents already using them.
- `src/lib/templates/library.ts` and `render.ts`: the new kinds; table and list markers (`<!-- required · table · …`); seeding into `.keel/templates`.
- `src/lib/settings/*`, `src/app/settings/*`, `src/app/(project)/setup/*`: four template selects (Task, Change request, Prompt for the coding agent, Changes index), "Code map for planning changes" and "Keep changes/README.md up to date".
- `src/lib/changes/store.ts`: `createChange` renders the body from the chosen `change-request` template; the assistant drafts Why, What changes and Done when as suggestions; `suggestDependsOn(cr, all)`; `idClashes(all)`.
- New `src/lib/changes/plan.ts`: `planChange(store, cr, codeMap)` → `{ tasks, scenarios, linked }`. One model call with the request, the updated documents, the traceability index and the code map (names only unless files are chosen). Validated with zod. Task IDs continue from the highest `R` number in `tasks/` and `changes/*/tasks/`.
- `src/lib/changes/flow.ts`: `packageFiles` renders `PROMPT.md` from `prompt@1` and tasks from `task@2`; includes accepted scenarios; adds links to decision records and mock screens.
- New `src/lib/changes/index-file.ts`: render `changes/README.md` from `changes-index@1`; called after raise, approve, reject and when a request becomes applied; skipped when `changesIndex: off`.
- `src/lib/repo/scan.ts`: `codeMap(root)` returns the file tree (names only, ignoring what the scan ignores).
- Change request page: step 4 "Plan the change" and step 5 package preview, as in `docs/mocks/source/Changes.dc.html`; task "As built" shown after read-back.

## As built

- **Templates:** `seed/templates/{change-request-v2,prompt,task-v2,changes-index}.md` (`change-request@2`, `prompt@1`, `task@2`, `changes-index@1`). `change-request@1` and `task@1` stay for documents that use them. The library has a "Change requests · request, prompt, tasks and index" group holding the change request, prompt, task and changes index kinds. `chosenTemplate`/`kindOptions` pick the configured version, else the newest.
- **Config and Settings:** `.keel/config.yml` › `templates.{task,change,change-prompt,changes-index}`, `code_map: off | names | files` (default `names`) and `changes_index: auto | off` (default `auto`). The "Templates for new documents" form (`ChangeTemplatesForm`) is in Settings › This project and in Project setup. Plans use the chosen task template.
- **Raising:** `createChange` writes the chosen change request template (`changes/body.ts`):
  - Why comes from the reason.
  - What changes and Done when come from the assistant's draft (`changes/draft.ts`, one call when raised from the Changes page), marked "Drafted by the assistant: edit it before approval".
  - Requirement changes and Impact are filled as tables.

  Requests raised by Explore, scenarios and design keep their own bodies.
- **Plan the change** (step 4, `changes/plan.ts`): one model call for an approved Keel request. It sends:
  - the request, the requirements' statements, the linked tasks and scenarios;
  - the code map (file and folder names from the R15 scan; nothing when Off);
  - with "files", only the files ticked on the page, capped.

  Tasks are numbered on from the highest R number in `tasks/`, `changes/*/tasks/` and earlier plans; listed files must be in the code map or marked "(new)". Scenarios are suggestions to Accept or Clear. Linked: decision records naming the requirements (and design records serving them), the current mock set's screens, suggested `depends_on` and ID clashes (`changes/links.ts`). The plan is `.keel/plans/CR-NNNN.json`, and the request records `planned_at`.
- **Package** (step 5): PROMPT.md from `prompt@1` (verify command from the handoff commands, the UI guide when tasks touch screens, a Linked section), one `tasks/R*.md` per planned task from `task@2` (with `change: CR-NNNN` and As built), and the accepted scenarios as `features/<request>.feature`. It is written in one Keel commit, together with the request's `package` list and changes/README.md. A request that was never planned keeps the earlier package (affected tasks and scenarios).
- **changes/README.md** (`changes/index-file.ts`): generated from `changes-index@1` and rewritten after raise, approve, reject, package and impact decisions (resolving the last document applies a request with no tasks). Skipped with `changes_index: off`. Open requests come first in dependency order, then applied ones, followed by the requirement IDs (clashes flagged) and how to run them.
- **ID clashes:** the Changes page tags both requests "ID clash · REQ-NNN" and offers "Use REQ-next in CR-later" for a Keel request (`renumberRequirement`). A hand-written one is told to change its file.
- **Not built:**
  - Editing the drafted text in Keel; the request is edited in its file.
  - "As built" shown on the change request page after read-back.
- **Commits:** steps 2 to 5 share files, so they are one commit after "Templates and Settings".
- **Fixed on the way:**
  - `seed/templates/task-v2.md` had invalid YAML; its `plan` field is now quoted.
  - An import cycle between `changes/store` and `changes/index-file`; the index path is a literal.

### CR-0011 comparison (step 6)

`src/lib/changes/compare-cr-0011.test.ts` (and `npx tsx scripts/compare-cr-0011.ts`) raises "Ollama is the default provider, with the local models listed" in a project whose code map is this repository's file names, plans it, accepts the suggested scenarios and writes the package. It ran with the fake provider; a real model was not used, because that would send the repository's file names to the configured provider.

- **Request:** generated Why, What changes, Requirement changes, Impact by requirement, Decisions, Done when. The hand-written CR-0011 has the same core, plus "Changes to apply to the documents"; its "Decisions" is absent.
- **Prompt:** 5 numbered steps (copy tasks and scenarios, implement in order and commit each as `<task ID>: <task title>`, working rules, As built, Done when). The hand-written CR-0011 prompt has 4.
- **Tasks:** one generated task (R1 in that empty project; R19 here). Hand-written: R16.
- **Files likely to change:**
  - Generated: `src/lib/providers/local.ts`, `src/lib/providers/ollama.ts`, `src/components/ModelUnavailable.tsx`, `src/lib/providers/azure-openai.ts`, `src/lib/providers/openai-compatible.ts`, `src/lib/providers/test-connection.ts`.
  - The hand-written R16 names `src/lib/providers/types.ts`, `src/lib/providers/ollama.ts`, `src/lib/settings/settings.ts`, the feature files and the Settings mock.
  - In both: `src/lib/providers/ollama.ts`. A real model would be expected to do better than the fake's word matching on names.
- **Scenarios:** 1 generated for REQ-009. The hand-written feature has 3.
- **Missing compared with hand-written:** the per-document changes ("Changes to apply to the documents") and multi-scenario coverage of one requirement. Those come from the model and the owner's edits.
