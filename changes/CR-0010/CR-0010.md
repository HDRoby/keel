# CR-0010: Opening a folder - four cases

## Why

`npx keel` can be run in four kinds of folder. CR-0004 covers the empty folder and adopting Keel documents (R9). It does not say what to do with a project that already has code, with or without its own AI setup.

## The rule for every case

When a folder has no `.keel/`, Keel first scans it **locally** (file names and manifests only, nothing sent to a model, nothing written) and opens Initialise with a **"What Keel found"** card and a recommended path. Nothing outside `.keel/` is written until the user acts, and an existing file is never changed without a per-file choice.

The scan looks for: git (repository, commits, contributors), code and manifests (`package.json`, `pyproject.toml`, `go.mod`, `Cargo.toml`, `pom.xml`, …), docs (`README*`, `docs/`, decision records), tests, AI agent files (`AGENTS.md`, `CLAUDE.md`, `.claude/`, `.cursor/rules`, `.cursorrules`, `.github/copilot-instructions.md`, `GEMINI.md`, `.windsurfrules`), and spec tools (Spec Kit `specs/`, `.kiro/`).

## The four cases

1. **New folder** (empty or no code). Today's Initialise flow, then a blank Explore. "Not a git repository yet: Keel will run git init."
2. **Already uses Keel** (`.keel/` exists). Open at the current stage. Before opening, check and show a notice only when something needs attention:
   - config format older than this Keel: offer to upgrade it in one Keel commit, listing what changes;
   - changes since the last run (agent or anyone else) are waiting in Read-back;
   - documents or template and standard versions named in `config.yml` but missing: a repair notice instead of an error.
3. **Existing project, no AI files.** Two paths; the first is recommended:
   - **Record what exists, then plan the next change.** The assistant drafts a **baseline**: intent sections, requirements marked "as built", and design decisions from the detected stack ("Keep current", recorded rather than decided). All are suggestions; the user trims and approves. The next idea is then a change request on the baseline.
   - **Treat the next feature as the project.** The intent covers only the new feature; the code is context and constraints.
   - **Opt-in reading.** "Let the assistant read these files" lists the files it would send (README, manifests, route and test names, a few key files) with sizes and a total. The user can untick any file or turn reading off and fill the sections by hand.
4. **Existing project with its own AI setup.** Same paths as case 3, plus:
   - existing agent files are **kept** and listed with what Keel will do: `AGENTS.md` gets only a Keel block between `keel:start` and `keel:end` markers at handoff; `CLAUDE.md` gets one pointer line if missing; same-name subagents become handoff conflicts;
   - **rules** found in agent files are proposed one by one as a project standard (`.keel/standards/project-conventions/SKILL.md`);
   - existing **specs** (Spec Kit, Kiro, PRDs) feed the baseline; their requirements get REQ IDs and keep the original IDs as aliases;
   - if `docs/`, `tasks/` or `features/` already mean something else, Keel proposes `keel/docs`, `keel/tasks` and `keel/features` (saved in `config.yml`).

The primary button follows the path: "Initialise and draft the baseline" or "Initialise and start brainstorm".
