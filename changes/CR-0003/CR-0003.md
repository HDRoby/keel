# CR-0003: Change requests across stages, and the Changes page

## Why

Once a document is approved it is not reopened (REQ-005): it changes through a change request. Keel has no change requests yet, although later work relies on them (CR-0005 "Save as change request", CR-0007 and CR-0009 after approval). The owner also wants the change requests he writes by hand, like CR-0004 to CR-0012, to be visible and tracked in Keel.

This was on the roadmap's Next list. It runs right after CR-0005 (R10), which is already built.

**Already built that this must absorb:** R10's "Save as change request" (`saveChangeRequest` in CR-0005) writes `docs/changes/NNNN-intent-change.md` from the change-request template. CR-0003 moves that to the format below: `saveChangeRequest` calls `createChange`, which writes `changes/CR-NNNN/CR-NNNN.md`, and any existing `docs/changes/*.md` is moved into `changes/` once, keeping its content, with the next free CR number.

## What changes

### 1. A change request is a folder in `changes/`

- `changes/CR-NNNN/CR-NNNN.md` with a header: `id`, `title`, `status` (`draft`, `waiting`, `approved`, `rejected`), `size` (`minor` or `significant`), `affects` (documents and versions), `requirements`, `depends_on`, `created`, `author`.
- Next to it, as the request needs: `PROMPT.md` (for the coding agent), `tasks/`, `features/`, `decisions/`, `docs/` (proposed document text), `mock-source/`.
- The same format whether Keel writes it or a person does. CR-0004 to CR-0012 already follow it.
- Numbers come from the highest `CR-NNNN` in `changes/` plus one; never reused.

### 2. Where change requests come from

- An edit to an approved document: Explore after the intent is approved ("Save as change request", CR-0005); a design decision changed after the spec is approved (CR-0007); a new mock set after approval (CR-0009).
- Roadmap: "Raise change request" on a Next item.
- **New change request** on the Changes page: title, reason, affected documents.
- A folder written by hand (or by another tool) in `changes/`: Keel picks it up on the next read.

### 3. The Changes page (side menu: Changes)

- **List** read from `changes/`: ID, title, meta (documents and versions, or folder and tasks), status, requirements, task progress, origin (Keel or written by hand). Filters: Open, Applied, All. Each row opens the request.
- **Status shown** is computed:
  - `Draft` and `Waiting for approval` from the header;
  - `Approved · waiting for CR-NNNN` when a request in `depends_on` is not applied;
  - `Approved · ready` when nothing blocks it;
  - `In progress` when some of its tasks are done;
  - `Applied` when all its tasks are done.
  Task status comes from the task files' `status` (copied to `tasks/` when the request is applied) and from read-back of the coding agent's commits.
- **Next to apply**: the first ready or in-progress request in dependency order, with "Copy prompt for the agent" (its `PROMPT.md`).

### 4. The change request page (one request)

As in the mockup's change request screen:
1. **What changed**: the diff of the source document, with the reason.
2. **Size and approval**: `minor` (wording, no requirement change) is approved with the document; `significant` (requirements added, removed or changed) needs an explicit approval of the new version.
3. **Impact on later documents**, by requirement ID: each affected document (spec, plan, tasks, scenarios, mock set) with what the change touches and three actions: **Update** (Keel regenerates the affected parts as a draft), **Still valid** (no change, recorded), **Later** (stays flagged out of date).
4. **Change package for the agent**: the request's `PROMPT.md`, tasks and scenarios written to `changes/CR-NNNN/`; at handoff it is written to the folder like the rest.

For a request written by hand, steps 1 to 3 show what its files say (affected documents, requirements, tasks); the user can approve or reject it.

### 5. Out of date, everywhere

While a significant request is approved but not applied, the documents it affects show **"Out of date · CR-NNNN"** in the stage bar, on the document page and in the plan's impact view, with a link to the request.

## Requirement changes

| ID | Change |
| --- | --- |
| REQ-014 (new) | Change requests across stages. A change to an approved document becomes a change request in `changes/CR-NNNN/`: diff, size, approval for significant changes, impact on later documents by requirement ID with Update / Still valid / Later, and a change package for the coding agent.
