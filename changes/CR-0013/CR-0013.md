# CR-0013: Change packages as complete as hand-written ones

## Why

The change requests CR-0003 to CR-0012 were written by hand, and the coding agent built them with few questions: each had a full description, new tasks with real file paths, scenarios, linked decisions and mocks, a prompt with working rules, and an index with the run order. What Keel generates today (R18) has the same folder and header, but much less inside: a short Reason and What changed, copies of existing tasks instead of new ones, "Files that are likely to change: To be decided by the coding agent", a five-line prompt, and no index. Keel should produce packages as good as the hand-written ones.

## What changes

1. **Templates for every file of a package**, versioned like the others, in `.keel/templates` and the library (Templates › "Change requests · request, prompt, tasks and index"):
   - `change-request@2`: Why, What changes, Requirement changes, Impact by requirement, Decisions, Done when;
   - `prompt@1`: read order, steps, working rules, report;
   - `task@2`: adds Data, Steps and **As built** to `task@1`;
   - `changes-index@1`: `changes/README.md` with status, order, requirement IDs and how to run them.
   The files are in `seed-templates/` in this folder.
2. **Settings › This project › Templates for new documents** gets four selects: Task, Change request, Prompt for the coding agent, Changes index. Project setup shows the same. The choice is saved in `.keel/config.yml` like the other templates; removing a template in use is blocked, as for the others.
3. **Writing the change request.** When Keel raises a request, the assistant drafts Why, What changes and Done when from the source change and the reason, and fills Requirement changes and Impact automatically. All drafted text is a suggestion the user edits before approval.
4. **Plan the change** (new step 4 on the change request page, after impact):
   - the assistant breaks the change into **new tasks**, numbered on from the highest R number, each with goal, requirements, data, steps and **files that are likely to change**;
   - it **suggests scenarios** for new or changed requirements (reusing CR-0006), as suggestions to accept or clear;
   - it lists what is **linked**: decision records the change creates or supersedes (CR-0007), mock screens for the affected requirements in the current mock set (CR-0009), a suggested `depends_on`, and requirement-ID clashes.
5. **Code map** (Settings › This project › "Code map for planning changes"): Off; **File and folder names only** (default, from the CR-0010 scan, nothing else read); or Names plus files the user chooses each time (with sizes shown before sending, like the baseline). Without a code map, tasks say "To be decided by the coding agent".
6. **The package** (step 5): `CR-NNNN.md`, `PROMPT.md`, `tasks/R*.md`, `features/*.feature` with the accepted scenarios, links to decision records and mock screens, written with the chosen templates as one Keel commit. Keel requests only; hand-written requests stay as written.
7. **`changes/README.md`** is generated from `changes-index@1` and rewritten whenever a request is raised, approved, rejected or applied (Settings › "Keep changes/README.md up to date": on by default; off keeps the user's own file).
8. **Dependencies and IDs.** When a request is raised, Keel suggests `depends_on` from open requests that touch the same documents or requirements. When two open requests name the same new REQ ID, both show a warning and the later one is offered the next free ID.
9. **As built.** After read-back, a task's "As built" section shows on the change request page under its task.
