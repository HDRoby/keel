# T5 · Requirement IDs and traceability index

## Goal

Parse REQ IDs from documents, task files and @REQ tags in feature files into the index, and answer "what does this requirement affect?".

## Scenarios that prove it

- `features/traceability.feature` › A changed requirement shows its impact (@REQ-004)

## Files that are likely to change

- `src/lib/trace/parse.ts`
- `src/lib/trace/index.ts`
- `docs/traceability.json (generated)`

## Notes

- IDs are never reused once assigned.
- Write docs/traceability.json into the handoff so agents can read it.
- As built:
  - `src/lib/trace/parse.ts` reads REQ IDs and statements from the intent and spec (`- REQ-001 …` items and `| REQ-001 | … |` rows). Task files link through their `requirements` front matter, or the IDs in the body. Feature files link through `@REQ-xxx` tags, feature-level tags included.
  - `src/lib/trace/index.ts` builds the trace from the project files. `latestIntentChange` compares the last two intent versions in git and lists the affected tasks and scenarios. `traceabilityJson` writes the `docs/traceability.json` format; T8a puts it in the handoff. Run on Keel's own repository, it reproduces `docs/traceability.json` exactly (unit test).
  - Screen: `/projects/[id]/trace`, linked from Explore. It shows requirements with their tasks and scenarios, plus the latest intent change and what it affects.
  - ID assignment (T4 question 4): when intent.md is drafted or updated from the brainstorm, Requirements statements get REQ IDs. Statements are list items, or the lines of the first answer when it has no list. Probe answers stay as prose. IDs are reserved through `next_req` in `project.md`, which only goes up and starts past any ID already used, so an ID is never reused. The brainstorm keeps the statement → ID map, so later versions keep the same IDs.
