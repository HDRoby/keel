# R11 · Edit acceptance scenarios in the Spec

## Goal

Scenarios are grouped by requirement and can be edited, added, deleted and suggested. The plan needs at least one per requirement.

## Scenarios that prove it

- `features/scenarios.feature` (all scenarios)

## Data

- Scenarios live in the spec's scenario store, saved as `features/<feature>.feature` when the spec is saved:
  `{ id, req, feature, name, steps: [{ keyword, text }], origin: 'user' | 'suggested' }`.
- The `@REQ-xxx` tag is written from `req`; it is not edited by hand.
- Parsing existing `.feature` files back into this shape uses the same parser as traceability (T5).

## Files that are likely to change

- `src/lib/trace/*`: `coverage(spec)` returns scenarios per requirement and the requirements with none.
- `src/lib/gates/*`: the plan gate adds "every requirement has at least one accepted scenario"; the locked message lists the requirements without one.
- `src/lib/generate/spec.ts`: the first draft proposes one scenario per requirement, as suggestions.
- New `src/lib/generate/scenario.ts`: `suggestFailureCase(requirement, spec)` asks the model for one failure scenario (validated with zod: name, steps with allowed keywords).
- New `src/lib/scenarios/gherkin.ts`: build the `.feature` text from the store, grouped by feature (pure function, unit tested).
- `src/app/(project)/spec/page.tsx`: the Acceptance scenarios tab as in the mockup: coverage line, groups per requirement, view and edit modes, + Add scenario, Suggest a failure case, Accept and Clear, Gherkin tab.

## Notes

- Follow the BDD style skill: behaviour, not clicks; one When per scenario where possible. Show a soft warning (not a block) when a scenario has no Then step.
- After the spec is approved, scenario edits go through a change request.
