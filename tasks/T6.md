# T6 · Stage gates, approvals, and spec and plan generation

## Goal

Enforce the stage rules and record approvals (approve, request changes, reject) with who, when and a comment.

## Scenarios that prove it

- `features/stage-gating.feature` › Spec is locked until the intent is approved (@REQ-005)
- `features/stage-gating.feature` › Approving the intent unlocks the spec (@REQ-005)

## Files that are likely to change

- `src/lib/gates/rules.ts`
- `src/lib/gates/approvals.ts`
- `src/components/StageBar.tsx`

## Notes

- Rules: Intent needs the required sections; Spec needs an approved intent; Plan needs a Go decision; Handoff needs an approved plan.
- Locked stages are greyed out, not clickable, and say why.
- A Go, Park or No-go decision is saved as docs/decisions/NNNN-*.md.
- As built:
  - `src/lib/gates/rules.ts` decides which stages are open. Intent opens when the required sections are captured, or once intent.md exists. Spec opens when the intent is approved. Plan opens when the latest decision is Go. Handoff opens when the plan is approved and the latest decision is Go.
  - `src/lib/gates/approvals.ts` handles reviews. Approve, Request changes and Reject set the status to approved, draft and closed. A review changes the status in place (owner decision: approving draft v1 gives approved v1). It records `approvals: [{action, by, date, comment, version}]` in the front matter and a commit such as "INT-0001 v1: Approved by Ada: Clear.". No new version is recorded; reindex keeps the first commit of each version. A closed (rejected) document cannot be reviewed again. Reviews on a locked stage are refused, in the code as well as the UI.
  - Decisions are recorded on the Spec stage as `docs/decisions/NNNN-go.md` (or `-park`, `-no-go`) from the decision-record template. They carry `decision`, `decided_by` and status approved. The latest decision counts.
  - Screens: a stage bar on every stage page (Explore, Intent, Spec, Plan, Handoff). Locked stages are greyed, not links, and show the reason. Opening a locked stage directly shows "Locked." with the reason.
  - Who reviews: there is no login (single user), so the form asks for a name, prefilled from git config `user.name`, else the project author.
  - Generate spec (owner decision): on the Spec stage, choose a spec template and click Generate spec.
    - Keel writes the Requirements table from the intent, with source.
    - It writes one `@REQ-xxx`-tagged scenario per requirement, using the model's scenario when it is well formed, to the Acceptance scenarios section and to `features/<slug>.feature`.
    - "Standards applied" says none are selected.
    - The model chosen for "documents" writes the other sections, and the "feasibility" model writes the feasibility review.
    - `from_intent` is recorded.
  - Generate plan (owner decision): on the Plan stage, fills the implementation-plan template.
    - Tasks come from the model as "T<n> | title | REQ IDs" lines. Only known IDs are kept, and any requirement left out gets a task of its own; with no model, there is one task per requirement.
    - Order of work is a table with the tasks, requirements and scenario files.
    - Each task gets `tasks/T<n>.md` from the task template, with status todo, `plan` and `requirements` front matter, its requirements under Goal, and its scenarios under "Scenarios that prove it".
    - `from_spec` is recorded.
  - When no model is available, a written section says "Not written yet … No model was available." instead of failing.
  - Regenerating (owner decision): a draft spec or plan (draft includes "changes requested") can be regenerated as its next version.
    - Keel keeps what it generated last in `.keel/generated/` in the project repository. It merges three ways: section by section for spec.md and plan.md, and per file for the feature file and each task file.
    - Only the proposer changed a piece: theirs stays. Only the generation changed it: the new text comes in. Both changed it differently: a conflict, recorded as `conflicts` in the header, and the proposer's text stays until it is resolved.
    - Plan tasks: new tasks are added. An unedited task the regeneration drops is removed. An edited task the regeneration changes or drops is a conflict.
    - A conflicts panel shows both sides. For each conflict choose Keep mine, Take new or a merged text; resolving saves the next version.
    - Approving is refused while conflicts are open (server-side). Request changes and Reject still work.
    - Approved documents are not regenerated; changing them is the change-request flow (CR-0003, Next).
  - Standards (owner decision): chosen at Start and in Project setup from the seed standards (copied to `KEEL_HOME/standards/`), and recorded as `standards` in `project.md`.
    - The spec header records them, and "Standards applied" lists them with versions and owners.
    - The rules of the standards that apply to the spec, or to the plan, go to the model with the sources, so Flagged concerns can name conflicts.
    - The Standards library screen and Agent kit selection stay in Next (roadmap updated).
