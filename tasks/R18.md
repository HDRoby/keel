# R18 · Change requests across stages, and the Changes page

## Goal

Change requests are folders in `changes/`, raised by Keel or written by hand, listed and tracked on the Changes page, with impact by requirement and a change package for the agent.

## Scenarios that prove it

- `features/change-requests.feature` (all scenarios)

## Files that are likely to change

- New `src/lib/changes/store.ts`:
  - `listChanges(root)`: read `changes/*/CR-*.md` headers (gray-matter + zod; unknown fields kept), the request's `tasks/*.md` and the matching files in the project's `tasks/` for status.
  - `computeStatus(cr, all)`: Draft, Waiting for approval, Approved · waiting for CR-NNNN, Approved · ready, In progress, Applied, Rejected (pure, unit tested).
  - `nextToApply(all)`: first ready or in-progress request in dependency order.
  - `createChange(root, { title, reason, source, affects })`: next number, folder, header, commit "Keel: Raise CR-NNNN".
  - A request whose header does not parse is listed with "Cannot read header" and the error line, not hidden.
- New `src/lib/changes/impact.ts`: from the source document's diff (versions/diff.ts) and the traceability index, list affected documents, tasks, scenarios and mock screens by REQ ID; `size` is significant when requirements change.
- New `src/lib/changes/package.ts`: write `PROMPT.md`, task files and scenario stubs for the request; Update regenerates affected parts as drafts (reuse generate/*).
- `src/lib/gates/*` and `StageBar`: out-of-date flags from approved, unapplied significant requests, with the request link.
- `src/lib/versions/*`: each version records `change: CR-NNNN` when it came from a request.
- Pages: `src/app/(project)/changes/page.tsx` (list, filters, Next to apply with copy prompt) and `src/app/(project)/changes/[id]/page.tsx` (what changed, size and approval, impact with Update / Still valid / Later, change package), as in `docs/mocks/source/ChangesList.dc.html` and `Changes.dc.html`.
- Hooks: `createChange` is what CR-0005's "Save as change request" (already built: switch `saveChangeRequest` from `docs/changes/NNNN-intent-change.md` to `createChange`), CR-0007's decision change after approval and CR-0009's new mock set call.
- One-off migration: move any `docs/changes/*.md` into `changes/CR-NNNN/CR-NNNN.md` (next free number, content kept, header mapped), as one Keel commit; update links that pointed to the old path.

## Notes

- Never rewrite a hand-written request's files; Keel only updates its header status on approve or reject, as a Keel commit.
- Read `changes/` on page load and after read-back; no watcher needed.

## Owner decisions (2026-11-22)

1. Approving a change request to the intent writes the next intent version from Explore, approved, with `change: CR-NNNN`; the request's approval is the approval of that version, minor or significant. Rejecting it puts Explore back to the approved text.
2. A request with no tasks is Applied once every affected document is resolved (Update done, or Still valid). Later keeps it open and the documents out of date.
3. Update makes the next version of that spec or plan a draft, regenerated from the changed upstream with the usual merge and conflicts, recording `change: CR-NNNN`; it then needs approval like any draft. Mock sets come with CR-0009.
4. R18 is in its own "Rework for CR-0003" section after R10, noting it runs after CR-0005.

## As built

- **Store** (`src/lib/changes/store.ts`):
  - `listChanges` reads every `changes/CR-NNNN/CR-NNNN.md` and keeps header fields it does not know; `README.md` and other entries are ignored.
  - Hand-written headers YAML cannot parse are read line by line (`lenientHeader`). CR-0005's own title has an unquoted colon, so this was needed for this repository.
  - A request with no usable id, title and status is listed as "Cannot read header" with the reason, not hidden.
  - Task status comes from the request's `tasks/*.md`, matched by name in the project's `tasks/` (which the coding agent updates and read-back sees), else the request's own copy.
  - `computeStatus` gives Draft, Waiting for approval, Approved · waiting for CR-x, Approved · ready, In progress, Applied, or Rejected.
  - `isApplied`: all tasks done; for a Keel request without tasks, every affected document resolved (owner decision 2). A hand-written request without tasks is never Applied.
  - `nextToApply` takes a request already in progress first, then the first ready one, in dependency order (cycles do not loop).
  - `createChange` uses the highest number plus one and commits "Keel: Raise CR-NNNN …". `setChangeStatus` changes only the `status:` line of a hand-written file, leaving the rest byte for byte; a Keel request gets its header rewritten.
- **Impact** (`impact.ts`): `changeImpact` takes the changed REQ IDs and the traceability index, and lists the later documents with the tasks (plan) and scenarios (spec) they reach. `sizeOf` is significant when requirements are added, removed or changed.
- **Flows** (`flow.ts`):
  - Submit, size, approve and reject.
  - Approving the request Explore raised writes the next intent version from Explore, approved, with `change: CR-NNNN` and IDs for new rows; rejecting puts Explore back to the approved text (owner decision 1). Requests raised elsewhere leave intent.md alone.
  - A minor Keel request has no impact to resolve, so approving applies it.
  - `decideImpact`: Update reopens the spec or plan as a draft, regenerates it from the changed upstream (merge and conflicts as usual) and records `change: CR-NNNN` (owner decision 3). Still valid and Later are recorded.
  - `writePackage` writes PROMPT.md, the affected task files and scenarios into the request's folder as one Keel commit.
- **Out of date** (`stale.ts`, REQ-005): approved, significant requests not applied flag their unresolved documents' stages and Handoff. The stage bar shows "Out of date · CR-NNNN", and the stage page shows a note linking to the request. A hand-written request flags only with `size: significant` (the requests in this repository have no size, so they flag nothing).
- **R10's Save as change request** now calls `createChange`: `changes/CR-NNNN/CR-NNNN.md`, waiting for approval, with the section diff, size, affected REQ IDs and impact. Saving again updates the same request while it waits. `migrateDocsChanges` moves any `docs/changes/*.md` into `changes/` once (next free number, content kept, header mapped, Explore's link updated) in one Keel commit; it runs on the Changes page and before a save.
- **Pages:**
  - Changes list: filters Open, Applied and All; "Next to apply" with "Copy prompt for the agent"; New change request (title, reason, affected documents).
  - Change request page `/changes/[id]`: 1 What changed (the request's text), 2 Size and approval, 3 Impact by requirement with Update / Still valid / Later, 4 Change package.
  - Roadmap: "Raise change request" on each Next item.
  - Explore links to the request waiting for approval.
- **This repository, adopted on a clone:** the Changes page lists CR-0003 to CR-0012. CR-0004 and CR-0005 are Applied, CR-0003 is Approved · ready and Next to apply, CR-0006 waits for CR-0003, and so on down the chain.
- **Tests:** store (including a copy of this repository's `changes/` and `tasks/`), statuses, dependency order, status-line-only edits, impact, the approve, reject and Update flows, minor requests, the package, out-of-date flags, and the one-off move (230 unit tests in all).
