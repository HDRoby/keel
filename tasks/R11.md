# R11 · Edit acceptance scenarios in the Spec

## Goal

Scenarios are grouped by requirement and can be edited, added, deleted and suggested. The plan needs at least one per requirement.

## Scenarios that prove it

- `features/scenarios.feature` (all scenarios)

## Data

- Scenarios live in the spec's scenario store, saved as `features/<feature>.feature` when the spec is saved:
  `{ id, req, feature, name, steps: [{ keyword, text }], origin: 'user' | 'suggested' }`.
- The `@REQ-xxx` tag is written from `req`; it is not edited by hand.
- Parsing existing `.feature` files back into this shape uses the same parser as traceability (T5).

## Files that are likely to change

- `src/lib/trace/*`: `coverage(spec)` returns scenarios per requirement and the requirements with none.
- `src/lib/gates/*`: the plan gate adds "every requirement has at least one accepted scenario"; the locked message lists the requirements without one.
- `src/lib/generate/spec.ts`: the first draft proposes one scenario per requirement, as suggestions.
- New `src/lib/generate/scenario.ts`: `suggestFailureCase(requirement, spec)` asks the model for one failure scenario (validated with zod: name, steps with allowed keywords).
- New `src/lib/scenarios/gherkin.ts`: build the `.feature` text from the store, grouped by feature (pure function, unit tested).
- `src/app/(project)/spec/page.tsx`: the Acceptance scenarios tab as in the mockup: coverage line, groups per requirement, view and edit modes, + Add scenario, Suggest a failure case, Accept and Clear, Gherkin tab.

## Notes

- Follow the BDD style skill: behaviour, not clicks; one When per scenario where possible. Show a soft warning (not a block) when a scenario has no Then step.
- After the spec is approved, scenario edits go through a change request.

## As built

- **Where scenarios live:** accepted scenarios stay in `features/*.feature`, the files the coding agent and traceability read, tagged `@REQ-xxx` from the requirement group. Suggestions wait in `.keel/scenarios.json` (`{ id, req, name, steps, origin: 'suggested', kind: 'draft' | 'failure' }`) and count only once accepted. Every change to that file is committed with the change it belongs to.
- **Gherkin** (`src/lib/scenarios/gherkin.ts`): `parseFeatureDoc` and `buildFeature` turn a feature file into data and back. Feature descriptions, a Background, tables and doc strings under a step, Examples and other tags are kept as written, so editing one scenario does not reformat the rest. A test round-trips every feature file in this repository. `warnings` gives the BDD style's soft warnings (no Then, more than one When); they never block.
- **Store** (`src/lib/scenarios/store.ts`):
  - `coverage` lists the spec's requirements with their accepted and suggested scenarios; `uncovered` lists the requirements with none.
  - Add, edit and delete scenarios. A new scenario goes into the feature file of the requirement's other scenarios, or into a new file named after the requirement. The group's tag is written from the requirement; other tags stay.
  - Accept, Clear and Accept all for suggestions.
  - `gherkinView` shows the `.feature` text per file, with held changes shown as they will be.
- **Gate** (`rules.ts`, REQ-005): Plan needs a Go decision and at least one accepted scenario for every spec requirement. The locked message names them: "Needs at least one accepted scenario for REQ-002".
- **Spec generation:** the first draft proposes one scenario per requirement as suggestions, instead of writing the feature file. Regenerate proposes scenarios only for requirements with none (accepted or suggested) and no longer merges feature files. The spec's Acceptance scenarios section points to the tab.
- **Suggest a failure case** (`src/lib/generate/scenario.ts`): one model call; the answer is validated with zod (a name, 2 to 15 steps with allowed keywords) and added as a suggestion. The fake provider answers with a scripted failure scenario.
- **After approval** (`src/lib/changes/scenarios.ts`): once the spec is approved, an edit, new scenario, deletion or accepted suggestion is held in `.keel/scenarios.json` and raised as a Keel change request (CR-0003), minor, with the before and after of each feature file. More edits go into the same request. Approving it writes the feature files; rejecting drops them.
- **Spec page** (`spec/scenarios-panel.tsx`, `scenario-editor.tsx`, `scenario-actions.ts`):
  - The Acceptance scenarios card has a coverage line, a group per requirement ("No scenario yet", or the count), scenario cards with Edit and Delete, and dashed, italic suggestions with Accept and Clear.
  - Under each group: "+ Add scenario" and "Suggest a failure case", plus "Accept all N suggestions" for the card.
  - The editor has the name, steps (keyword and text), add and remove step, Done and Cancel.
  - A Gherkin view, and a notice with the pending change request once the spec is approved.
- **Fixed on the way:** an action that redirected to the same address with only a `#anchor` did not reload the page, so a new suggestion stayed hidden. The scenario and change-request actions now revalidate first.
- **Tests:** gherkin round trips, the store (coverage, gate message, add, edit and delete keeping the file, suggestions, accept all, held edits approved and rejected), and the updated generation tests. Fixtures that go from spec to plan accept the draft's scenarios first. All four scenarios pass. The stage-gating step "the stage is locked" now reads the stage from the page, so the Plan scenario shares it.
- **Numbering:** this change is spec v10 and plan v10, because CR-0003 took v9.
