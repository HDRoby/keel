# CR-0014: Run Keel with one command, published as keel-sdlc, without SQLite

## Why

Today Keel runs from a clone: `git clone`, `npm install`, optionally `npm run build`, `npm link`, then `keel`. That is too much for anyone who just wants to try it, and `npx keel` runs an unrelated npm package that already owns the name `keel`. The owner wants one short command.

Keel also still ships SQLite (`better-sqlite3`, the only native module) for an index in `.keel/cache/index.db` that is written but never read: documents, versions and traceability already come from the files and git, and settings moved to `~/.config/keel` (R2). Removing it makes the package smaller, removes the only platform-specific binary, and makes `npx` reliable on every system.

## What changes

0. **No SQLite.** Remove the index and the `better-sqlite3` dependency before packaging:
   - `src/lib/store/db.ts` and the `Index` type: `Store` keeps `root`, `user` and `now`; every `index.upsertDocument`, `index.addVersion`, `index.clear` and `index.transaction` call goes. Nothing reads the index today, so behaviour does not change.
   - `src/lib/store/reindex.ts` and the `reindex` subcommand go. `versionFromCommit` (used by `src/lib/versions/diff.ts`) moves to `src/lib/versions/`.
   - `src/lib/settings/migrate.ts` (the one-off move from v0.1's `~/.keel/keel.db`) and its test go; the owner has already migrated.
   - `next.config.mjs`: drop `serverExternalPackages: ['better-sqlite3']`.
   - `.keel/cache/` keeps only the run lock (`run.json`); the Initialise list and the handoff file list say so.
   - Sample data that offers "Markdown in git with a SQLite index" as a storage option (fake provider, `/dev/ui`, the design-decisions scenario) becomes "Markdown files in git", with "A single database file" as the alternative.
   - A new decision record supersedes ADR-0007.
1. **Package name `keel-sdlc`.** The command stays `keel` (`bin: { "keel": "bin/keel.mjs" }`). The package becomes public (`private: false`) with `version`, `description`, `license`, `repository`, `keywords`, `engines.node >= 20` and a `files` list.
2. **One command, nothing to clone:**
   ```
   npx keel-sdlc                 # open the current folder
   npx keel-sdlc ~/my-idea       # open or create another folder
   npm i -g keel-sdlc            # optional: then just "keel"
   ```
3. **Pre-built.** The package contains a production build made with Next.js `output: 'standalone'`, so `npx` neither installs dev dependencies nor builds. `bin/keel.mjs` starts the standalone server (`node .next/standalone/server.js` with `HOSTNAME=127.0.0.1`, `PORT` and `KEEL_PROJECT_DIR`) when present, and falls back to `next dev` only in a clone without a build.
4. **Works from any folder.** Keel finds its own files (seed templates, styles, standards, agent kit, static assets) relative to its install folder, not the current working directory. `KEEL_SEED` still overrides.
5. **No native modules.** After step 0 the package is plain JavaScript: nothing is compiled or downloaded per platform at install time. A test fails if a dependency with native code is added.
6. **Subcommands without dev tools.** `keel import` (today `npm run keel -- import` through `tsx`) is compiled into the package. `keel --version` prints the version.
7. **Size and speed.** The published package stays under 25 MB unpacked; `npx keel-sdlc --version` answers in under 10 seconds on a clean machine with a warm npm cache.
8. **Release.** A GitHub Actions workflow publishes on a version tag (`v*`): `npm ci`, `npm run verify`, `npm run build`, `npm pack`, a smoke test of the packed file, then `npm publish --provenance` with an `NPM_TOKEN` secret. No secrets in the repository.
9. **Smoke test in CI.** On every push: pack the build, install the `.tgz` into an empty temporary folder, run `keel --version`, `keel --dry-run /tmp/demo --create`, and start `keel --no-open` on a fresh folder until the Startup check page answers, on macOS, Linux and Windows.
10. **Docs.** README quick start becomes the single `npx keel-sdlc` line (plus the global install); "Developing Keel" keeps the clone steps. The user guide's "Before you start" follows.

## Decisions

- New decision record: "No database: documents, versions and traceability come from the files and git" (ADR-0017). It supersedes ADR-0007; mark ADR-0007 `status: superseded by ADR-0017`.
- New decision record: "Publish as keel-sdlc with a standalone build; the command stays keel" (ADR-0016, written when this is applied). Alternatives considered: running from a clone (current), installing from GitHub with a `prepare` build (slow first run), a single executable or desktop app (later).
