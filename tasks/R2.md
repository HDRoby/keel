# R2 · User config folder for settings and secrets

## Goal

Move provider settings, keys and the model per task out of `keel.db` into the user config folder (ADR-0011).

## Scenarios that prove it

- `features/project-folder.feature` › Keel never writes keys into the project folder

## Files that are likely to change

- New `src/lib/settings/user-dir.ts`: `userDir(env)` = `KEEL_USER_DIR` or `$XDG_CONFIG_HOME/keel` or `~/.config/keel`. Created with mode 0700.
- `src/lib/settings/secrets.ts`: key file in `userDir()`.
- `src/lib/settings/settings.ts`: read and write `settings.json` (atomic write, mode 0600) instead of `store.index.getSetting`.
- `src/app/settings/*` (moved by R4).

## Notes

- One-off migration: if `~/.keel/keel.db` and `~/.keel/secret.key` exist and `settings.json` does not, copy the provider settings across, decrypting with the old key and encrypting with the new one. Log "Moved settings from ~/.keel" without values.
- Add a unit test that writes a key through Settings and then scans every file under the project folder (including `.keel/`) for the key and for `sk-` and `ghp_` patterns.
- Author default: `git config user.name`, then the value in `settings.json`.

## As built

- `src/lib/settings/user-dir.ts` (written in R1): `userDir(env)` = `KEEL_USER_DIR`, else `$XDG_CONFIG_HOME/keel`, else `~/.config/keel`, created with mode 0700. `settings.json` is written atomically with mode 0600; `secret.key` (0600) is in the same folder. `legacyHome(env)` (`KEEL_HOME` or `~/.keel`) is only used to find v0.1 data. This file is the only place in `src` that reads the home folder.
- Settings keys in `settings.json`: `provider.<id>` (connection details, key encrypted), `model.<task>`, `github.token` (encrypted, for CI results only after R8) and `author`.
- **Migration** (`src/lib/settings/migrate.ts`): when `settings.json` does not exist and `~/.keel/keel.db` does, providers, models per task and the GitHub token are copied across. Keys are decrypted with the old `~/.keel/secret.key` and encrypted with the user folder's key. A key that cannot be decrypted is dropped and named in the log line ("enter again"). The log line has names only: "Moved settings from ~/.keel to ~/.config/keel: …". It runs once per server process, and only for the real user folder: a run with `KEEL_USER_DIR` set (tests, another profile) skips it unless `KEEL_HOME` is also set, so test runs never copy the owner's keys.
- **Author default** (`defaultAuthor`): `git config user.name` read in the project folder, then `author` from `settings.json`. Settings has a "You" card with "Your name"; the Start form and the review forms use the default. The full Settings split ("You, on this computer" and "This project") is R4.
- **Tests:** `no-secrets-in-project.test.ts` saves Anthropic, OpenAI and GitHub keys through Settings on an initialised folder with documents, then scans every file under the project folder (`.keel/` and `.git/` included) for the keys and for `sk-ant-`, `sk-proj-` and `ghp_` patterns. `migrate.test.ts` covers the move, re-encryption, name-only logging and dropped keys.
- The scenario "Keel never writes keys into the project folder" passes: it saves a key on the Settings page, scans the project folder (index and git objects included) and checks `settings.json`, `secret.key` (0600) and that the key decrypts.
- **Change found by the scenarios:** recording the assistant's question no longer makes its own commit. The transcript is written, and committed with the next answer. Otherwise opening Explore right after Initialise added a commit, so "the last commit is Keel: Initialise project" was a race.
