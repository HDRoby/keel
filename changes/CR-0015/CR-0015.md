# CR-0015: AI readiness report, on demand, for any folder

## Why

When Keel opens a project that has no AI files, or AI files that do not follow the Keel standard, the owner wants to know how ready the folder is for coding agents, what could be added and why. The same check is useful on a Keel project, to find what has drifted (a command in AGENTS.md that no longer exists, a key file not ignored by git).

Rules alone give generic advice; a model alone invents files and gives generic advice too, especially a small local one. So **rules find the gaps and the model explains them**: the scan is local and testable, and the model adds the "why for this project", the order, and a review of the AI files the user chooses to share.

## What changes

1. **On demand only.** The check never runs by itself: not when a folder opens, not at Initialise. It runs when the user presses **Run the check**.
2. **Any folder.** It works the same for the four cases of `scanFolder` (`new`, `keel`, `existing`, `existing-ai`), including Keel's own repository.
3. **Where.** A new screen **AI readiness report** (route `/readiness`):
   - in the project menu of a Keel folder ("AI readiness", after Changes);
   - in the menu of a folder that is not initialised ("This folder": Initialise, AI readiness);
   - as an optional card in Initialise › What Keel found: "Want to know how ready this folder is for coding agents?" with **Check AI readiness**.
   It needs a working model, so it is not available in setup mode (CR-0012).
4. **Before running** the screen shows:
   - Step 1, the scan: file names and manifests, compared with the Keel standard; no model call.
   - Step 2, the model review, with the model used: the **Feasibility review** model from Settings.
   - **Files the model may read**: the AI files found (agent files, rule folders, subagents, skills, `.keel/standards`), each with a checkbox, ticked by default for agent instruction files. Files that may hold keys (`mcp.json`, `.env*`, anything matching the secret patterns below) are listed but cannot be ticked: "May contain keys: never sent".
   - A line saying exactly what will be sent: "file and folder names and N items you ticked. Never keys, .env files or files you did not tick."
5. **The scan (no model).** `scanFolder` plus the readiness rules in the table below. Rules may read files **locally** (as R15 does for rules in agent files); nothing is sent. Each rule returns pass, fail or not applicable, with the paths it is based on.
6. **The model review.** One short call per area (six calls), so small local models cope. Each call gets: the folder case, the file and folder names (the code map, names only), the rule results for that area, and the content of the ticked files relevant to that area (capped like the baseline: 100 KB per file, 200 KB in all). It answers in a fixed JSON format (see Data in R21):
   - a short "why it matters here" for each failed rule;
   - up to three extra findings per area, each with evidence (path, optional line);
   - impact (High, Medium, Low) and effort (Small, Medium, Large) for each piece of advice.
7. **Grounding.** Keel drops any finding or advice whose evidence names a path that is not in the scan, or a line beyond the end of the file. The model can lower an area from Ready to Partly with evidence; it can never raise a rating set by the rules.
8. **If the model fails** (timeout, invalid answer twice, provider error) the report still shows the rule results with standard "why" texts and a notice "The model review did not finish: <reason>". Run again is offered.
9. **The report** shows:
   - counts of areas Ready, Partly, Missing; date, model, time taken, which items were read;
   - six area cards (Agent instructions, Project knowledge, Verification, Conventions, Agent tooling, Safety) with a rating, a one-line finding, the paths, and whether it came from the scan or the model review;
   - for folders with AI files (`existing-ai`, `keel`): **Your AI files and the Keel standard**, a table of each agent file, its Keel equivalent and a proposal (Keep, Point to, Adopt), from the R15 handoff rules, with no model call;
   - **Advice**, in order of impact: title, area, why, based on (paths), impact, effort, source (Scan or Model review), and a choice **Add** (Keel creates or changes it), **Adopt** (keep yours, Keel uses it) or **Ignore** (hidden in the next report);
   - **Earlier reports**, with Compare (ratings and advice that changed).
10. **Acting on the advice** (one button, label depends on the folder):
    - Keel folder: **Create change request CR-NNNN**: a draft change request through the CR-0013 package writer, one task per accepted item (Add or Adopt), `requirements: []` unless an item names a requirement.
    - Not initialised (`existing`, `existing-ai`): **Add to the baseline plan**: the accepted items are stored with the report; Initialise preselects what matches (agent kit files, standards, adopting rules from agent files, AGENTS.md markers) and the rest become tasks in the baseline plan under "From the readiness report".
    - `new`: **Initialise this folder** opens Initialise.
11. **Saved and versioned.** The report is written from the template `readiness-report@1` to `.keel/reports/readiness-YYYY-MM-DD[-N].md` and committed as a Keel commit. In a folder without `.keel/` it is kept in `~/.config/keel/reports/<folder id>/` and moved into `.keel/reports/` by Initialise. The report holds names, ratings, advice and choices; **never file contents and never secret values**.
12. **Settings.** "Templates for new documents" gets **Readiness report**; "This project" gets nothing else. The report uses the Feasibility review model.

### Readiness rules (the Keel standard)

| ID | Area | Passes when | Advice when it fails | Impact · effort |
| --- | --- | --- | --- | --- |
| AI-01 | Agent instructions | `AGENTS.md` exists | Add AGENTS.md, drafted from the scripts and README | High · Small |
| AI-02 | Agent instructions | Every other instruction file (CLAUDE.md, GEMINI.md, `.github/copilot-instructions.md`, `.windsurfrules`) points to AGENTS.md, or there is only one | Make AGENTS.md the single source | High · Small |
| AI-03 | Agent instructions | Every `npm run`, `pnpm`, `yarn`, `bun run`, `make` command named in agent files exists in `package.json` scripts or the Makefile | Fix the command in <file> | High · Small |
| AI-04 | Agent instructions | The package manager named in agent files matches the lockfile | Use <manager> everywhere | Medium · Small |
| PK-01 | Project knowledge | README exists and has a section on running or developing | Add how to run it to the README | Medium · Small |
| PK-02 | Project knowledge | Requirements exist (`docs/intent.md`, `docs/spec.md`, Spec Kit or Kiro specs) | Record requirements as a baseline | Medium · Medium |
| PK-03 | Project knowledge | Decision records exist (`docs/decisions/`, `docs/adr/`, `adr/`) | Record the main decisions as a baseline | Medium · Medium |
| VE-01 | Verification | A test runner is configured and test files exist | Add a test runner and a first test | High · Medium |
| VE-02 | Verification | A CI workflow runs the test script | Run the tests in CI | High · Medium |
| VE-03 | Verification | Acceptance scenarios exist; in a Keel folder, every requirement has one (the R11 gate) | Add scenarios for <REQ IDs> | Medium · Medium |
| CO-01 | Conventions | Lint or format config exists | Add a linter config | Low · Small |
| CO-02 | Conventions | Conventions are readable by agents (`.keel/standards`, skills, or rules in agent files) | Turn the lint config into a standard | Low · Small |
| AT-01 | Agent tooling | A verifier subagent or equivalent exists (`.claude/agents/`, agent kit) | Add a verifier subagent | Medium · Small |
| AT-02 | Agent tooling | Rules are not limited to one tool (not only `.cursor/rules` or only `.windsurfrules`) | Adopt the <tool> rules as standards | Medium · Small |
| SA-01 | Safety | `.gitignore` covers `.env`, `.env*.local`, `*.pem`, `*.key` | Add <patterns> to .gitignore | High · Small |
| SA-02 | Safety | No tracked file looks like a secret: names (`.env`, `*.pem`, `id_rsa*`, `credentials*.json`) or a key-like field with a value (`apiKey`, `token`, `secret`, `password`) in JSON, YAML or TOML config | Remove the key from <file>, move it to an environment variable and rotate it | High · Small |

Area rating: **Ready** when every applicable rule passes, **Missing** when every applicable rule fails, otherwise **Partly**. In a `new` folder every area is Missing and the only advice is "Initialise the folder with Keel".

SA-02 reports only the file and the field name ("a value named apiKey"). The value is never shown, logged, sent or written to the report.

## Decisions

- New decision record ADR-0018 "AI readiness: rules decide, the model explains". Alternatives considered: model only (ungrounded, varies by model), rules only (no project-specific why, no review of the content of AI files).
- The report uses the Feasibility review model instead of a fourth model task (owner can change this later).

## Done when

- `npm run verify` passes, including `features/ai-readiness.feature`.
- Opening a folder or initialising one makes no readiness model call (fake provider records none).
- The report runs on the four fixture folders and gives the expected ratings (rule unit tests).
- The fake provider receives only names and the ticked files; a file matching the secret patterns cannot be ticked, and no secret value appears in the request, the page, the logs or the report.
- Advice naming a path outside the scan is dropped.
- With the model failing, the report still shows the rule results.
- In a Keel folder, accepting two items creates a draft change request with two tasks.
- Reports are saved, listed and compared.
