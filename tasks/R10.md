# R10 · Sections with live comments

## Goal

Explore shows the intent template's sections as fields. The assistant reviews all of them together and writes a comment on top of each one, without send buttons.

## Scenarios that prove it

- `features/brainstorm.feature` (all scenarios)

## Data

- Saved in `.keel/brainstorm/<intent id>.json` (committed, like the transcript), one entry per section:
  `{ key, value | rows: [{ id?, text, origin }], origin: 'user' | 'suggested' | 'accepted', cleared?, reviewedHash, comment: { kind: 'challenge' | 'link' | 'suggest' | 'ask' | 'ok', text, linkTo?, rewrite?, dismissed?, applied? }, thread: [{ from: 'user' | 'assistant', text, rewrite?, applied? }] }`.

## Files that are likely to change

- `src/lib/brainstorm/sections.ts`: sections from the template, required flags, progress. Only `user` and `accepted` values count.
- `src/lib/brainstorm/review.ts` (new):
  - `reviewAll(sections, template, style, focus?)`: one model call. The prompt has every section, its value, the template and the style. The answer is validated with zod: `{ comments: { [key]: comment }, suggestions: { [key]: text } }`. Unknown keys are ignored.
  - Suggestions are applied only to empty sections that the user has not cleared.
  - Never writes into a section with `origin: 'user'`.
  - `replyInThread(sections, key, userText)`: same context, answers in that section's thread, then refreshes the other comments.
- `src/lib/brainstorm/scheduler.ts` (new, client side):
  - Triggers: leaving a field with a changed value; a 5-second pause after a meaningful change (finished sentence, or 20 or more characters); Enter in a reply line; opening Explore if anything changed.
  - Fingerprint per section, so an unchanged list is not sent.
  - One call at a time, at most one every 10 seconds, latest change wins. Typing cancels the call in flight (AbortController) and waits for the next pause.
  - Settings (user level): pause length and minimum interval.
- `src/app/(project)/explore/page.tsx`: fields with the comment on top. The focused section shows its comment and thread in full; others show a one-line preview and a "New comment" tag. A status line shows "Reviewing all sections…" or when the list was last reviewed. Apply, Dismiss, Accept and Clear as in the mockup. Remove the chat panel, "Ask me the next question" and "Use a suggested answer".
- `src/lib/generate/intent.ts`: one pure function `intentMarkdown(sections, project, template, style)`, with no model call, used by Draft intent.md. Unaccepted suggestions are left out. New requirement rows get IDs from `reserveRequirementIds`; rows that already have an ID keep it; removed IDs are never reused.
- Requirements section: rows with an ID label ("new" or "suggested" before the first draft), Add requirement, move up, remove, and Accept or Clear for suggested rows. The review can return `addRow` instead of `rewrite` for this section.
- After approval: Explore shows a notice and "Save as change request" instead of Draft intent.md. Saving creates a change request with the section diff and the affected REQ IDs (uses CR-0003 when it exists; until then, a draft intent version marked as a pending change).
- Intent page: a notice that the file is assembled from Explore, a "Change in Explore" link, and headings that follow the template.
- Templates: the intent template declares `Requirements` as a list section (`type: list`). If the shipped template lacks it, publish a new template version. Unaccepted suggestions are left out; empty sections become "_Not written yet._".
- The fake provider returns scripted reviews keyed on section content, so the scenarios stay deterministic.

## As built

- **Template:** `seed/templates/intent-standard-v4.md` publishes **Standard intent v4** with the mockup's sections: Problem, Who it is for, Desired outcome, Scope, Requirements (`<!-- required · list · … -->`), Constraints, Open questions. Four are required. It is the default on Initialise; folders on v3 keep v3. `parseSections` reads the `list` marker, and a section called Requirements is always a list, so v3 works too.
- **State** (`src/lib/brainstorm/session.ts`, owner decision 2): `.keel/brainstorm/INT-0001.json` holds, per section, the value or rows (`id?`, `text`, `origin`), `origin` (`user`, `suggested`, `accepted`), `cleared`, `reviewedHash`, the comment (`kind`, `text`, `linkTo`, `rewrite`, `addRow`, `dismissed`, `applied`), `commentAt` and the thread. It also keeps `drafted` (each section's text at the last draft) and `changeRequest`. It is written on every change and committed at Initialise, Draft intent.md, Save as change request and Project setup. CR-0004's `explore.md` is converted on first read (answers become the user's text); Adopt and import produce the new form.
- **Gate:** only `user` and `accepted` text counts (`counts`, `requiredFilled`), and Requirements needs a row. Typing in a suggested section makes it the user's text; emptying a suggestion counts as Clear, and the assistant never refills a cleared section.
- **Review** (`src/lib/brainstorm/review.ts`): `reviewAll` makes one call. The prompt holds the style, the rules, and every section as JSON with who wrote it. The answer is validated with zod; unknown sections are ignored.
  - It returns the answer with the fingerprints it saw. `applyAnswer` puts it into the latest state, so edits made while the call ran are kept and reviewed next time.
  - Suggestions go only into empty sections that are not cleared, never into the user's text. A section the assistant just filled needs no review of its own.
  - A reply is answered in that section's thread, and the other comments are refreshed in the same call.
  - Token use is logged as an estimate (characters / 4), never the content.
- **Scheduler** (`scheduler.ts` rules, used by `explore/board.tsx`): a review when you leave a changed section, after a pause following a meaningful change (a finished sentence or 20+ characters), on Enter in a reply line, and once on opening (the server skips it when nothing changed). One review at a time, at most one per interval, latest change wins; typing aborts the request in flight. The pause and interval are user settings (Settings › Explore reviews; default 5 and 10 seconds).
- **API:** `POST /api/explore` with `save`, `review`, `reply` and `action` (accept, clear, apply, dismiss, add-row). It replaces `/api/brainstorm`.
- **Explore page:** section cards in template order, each with its comment on top (Challenge, Links sections, Suggestion, Question, Looks good).
  - The section you are typing in shows the full comment, the offered text with Apply and Dismiss, "Add as requirement", the thread, and the reply line. Others show a one-line preview with "Show".
  - A "New comment" tag marks a comment that changed after you last saw that section; first comments are not tagged.
  - Also: a status line ("Reviewing all sections…" or the time of the last review), the progress line, and Draft intent.md, or Save as change request once the intent is approved. Suggestions are in italics with Accept and Clear.
  - Requirement rows show their ID ("new" or "suggested" before the first draft), with move up, remove and "+ Add requirement".
  - The stage bar refreshes when the filled count changes.
  - Removed: the chat panel, "Ask me the next question", "Use a suggested answer" and "Add to a section".
- **intent.md** (`src/lib/generate/intent.ts`): `intentMarkdown` is pure, with no model call. Each section goes in exactly as written; unaccepted suggestions are left out, and empty sections read "_Not written yet._". `draftIntent` gives new rows IDs from `reserveRequirementIds`; IDs never change and are never reused. It saves v1, or the next draft version while the intent is a draft, and refuses once it is approved.
- **After approval** (owner decision 3): `saveChangeRequest` writes `docs/changes/NNNN-intent-change.md` (change-request template, status draft) with the before and after of each changed section and the affected REQ IDs. Saving again updates the same change request; `docs/intent.md` is not touched. Explore shows the approval notice and a link to the pending change request.
- **Intent page:** a note that the file is assembled from Explore, and "Change in Explore".
- **Fake provider:** scripted reviews keyed on content (challenges short text, links Constraints to "Who it is for" when product managers appear without a web UI, suggests Desired outcome and three requirement rows, comments carry the word count). `KEEL_FAKE_LOG` logs every model call so a scenario can check that drafting makes none.

  - Clicking Accept or Apply used to expand the comment on mousedown and lose the click.

The scenarios that drove the chat (stage gating, intent document, brainstorm styles, providers) now fill sections and reply in a thread, with the same wording.
