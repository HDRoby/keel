# R17 · Startup check and setup mode

## Goal

Check settings, model access and project config at startup; if anything fails, open in setup mode and let the user fix it first.

## Scenarios that prove it

- `features/startup-check.feature` (all scenarios)

## Files that are likely to change

- New `src/lib/startup/check.ts`: `runStartupCheck({ userDir, projectRoot })` returns `{ ok, checks: [{ id: 'settings' | 'provider' | 'models' | 'project', state: 'ok' | 'bad' | 'waiting', message, fix? }] }`. Later checks are `waiting` when an earlier one fails. Total budget 2 s; each network call has a timeout.
  - settings: zod schema of `settings.json`; decrypt test of stored keys.
  - provider: Ollama `GET /api/tags`; cloud providers a cheap authenticated call (model list).
  - models: each task's model exists in the provider's list; one test message ("Reply with OK") to each distinct model, result cached in `~/.config/keel/health.json` for 10 minutes.
  - project: `validateConfig(root)` from R15 returns errors with line numbers; referenced templates, styles and standards must exist in `.keel/`.
- `bin/keel.mjs` / `src/cli.ts`: run the check before starting the browser; print one line when OK, or the failing check and "setup mode".
- New `src/app/check/page.tsx`: the Startup check page as in `docs/mocks/source/Startup.dc.html` (no mockup case switcher).
- Route guard (Next.js middleware or the project layout): while the latest check fails, every route except `/check`, `/settings` (and `/setup` when the project check fails) redirects to `/check`. API routes that call a model return 503 with the check message.
- `src/components/ui/Shell`: setup-mode menu (Setup: Startup check, Settings, Project setup when relevant; the project group shown locked).
- Settings: after saving, re-run the check; if it passes and the user came from `/check`, go to the project.
- Model calls during a session: map connection and auth errors to the same messages, with a link to `/check`.

## Notes

- Never log keys or test-message content; log check ids, states and durations only.
- The fake provider and the fake Ollama stub make the scenarios deterministic.

## As built

- **Check:** `src/lib/startup/check.ts`. `runStartupCheck` runs four checks in order. When an earlier check fails, the later model checks are Waiting.
  1. Your settings: `settings.json` exists and is valid JSON, and the stored keys decrypt.
  2. Model provider: Ollama answers and has models; a cloud provider has its key.
  3. Models for each task: every task has a model, Ollama's are installed, and each distinct model answers a short test message.
  4. Project config: the config parses, and every template, style and standard it names exists. The message gives the line number and the line.

  Settings, provider and models are cached in `<user folder>/health.json` for 10 minutes, keyed on `settings.json`, so the test message is not sent on every page; saving any setting starts afresh. The project config is checked on every request (it is cheap). Only check ids, states and durations are logged. `startupLines` gives the terminal output: one "Startup check: settings OK · …" line, or the failing check and "Keel opens in setup mode".
- **Setup mode:** `src/proxy.ts` (Next 16's Proxy) only passes the path in a header. The root layout runs the check and redirects every page except `/check` and `/settings` (and `/setup` when the project config is the problem) to `/check`. The side menu becomes "Setup" (Startup check, Settings, Project setup when relevant) with the project group shown as locked. `/api/explore` answers 503 with the check's message.
- **Startup check page:** `/check`, as in `Startup.dc.html`:
  - the title for each case: Set up Keel first, Keel cannot reach your model, A model is missing, This project's config has a problem, All set;
  - each check with OK, Needs fixing or Waiting, the reason, the wrong line when there is one, and the fix;
  - the setup-mode notice, the button to Settings or Project setup, and Check again (which runs afresh and opens the project when everything passes).
- **First run:** Settings shows "Set up Keel first" with "Use these settings and check", which saves the preselected Ollama models and checks again.
- **Terminal:** `npx keel` (`bin/keel.mjs`) waits for the server, prints `/api/startup`'s lines, and opens the browser on `/check` in setup mode. `npm run keel -- check --dir <folder>` runs the same check from the command line (the scenarios use it).
- **Fixed on the way:** an import cycle between `skill-files` and `templates/library`, which showed only when a route loaded them in the startup check's order. `VERSIONED_REF` now lives in `src/lib/refs.ts`.
- **Tests:**
  - The fake provider logs the startup test message as `health`, and the steps' `modelCalls()` leaves it out: it carries no project content.
  - Unit tests in `src/lib/startup/check.test.ts` (5) and `features/steps/startup-check.steps.ts` (5 scenarios).
- **Checked with the real command:** no settings file → setup mode; with settings and the Ollama on this computer → "Startup check: settings OK · Ollama running, 5 models · test message answered".
- **Not built:** cloud providers are checked by key presence plus the test message, not a separate model-list call.
